    summary: 약 20개 테이블에 분산된 BL 조회 모델을 Cosmos DB 단일 문서로 통합

      - 평균 응답 시간 약 1,000ms → 500ms
      - REST 전환 후 기존 연결·프록시 오류 미발생
    evidence: 운영 환경에서 동일한 조회를 약 30회 측정한 평균 응답 시간
    team: 총 7명 · 백엔드 4명 · 프론트엔드 1명 · QA 2명
    role: 백엔드 개발 · 조회 API의 Cosmos DB 전환 및 QA·배포 일정 조율
    collaboration: 백엔드 개발자들과 다수 API 전환과 데이터 검수를 공동 수행하고, 프론트엔드·QA와 이슈 단위로 직접 협의
    stack: Java · Kotlin · Spring Boot · Azure Cosmos DB · Kubernetes · gRPC · REST
    problem: |
      한 화면을 위해 다수 테이블과 API를 조합해야 해 필드 추가나 조회 조건 변경 시 영향 범위가 계속 커졌습니다.
      추가로 같은 도메인의 결과를 각각의 애플리케이션에서 따로 조회하는 현상이 발생하여 데이터 변경 시 모든 애플리케이션을 수정해야 하는 불편함이 있었습니다.
    actions:
      - 한 화면의 조회에 필요한 데이터를 한 번에 제공하기 위해 사용 사례를 기준으로 Cosmos DB 문서 경계를 정의하고 쓰기 모델과 조회 모델의 책임 분리
      - 데이터 변경 시 애플리케이션마다 수정해야 하는 문제를 줄이기 위해 분산된 조회 책임을 전담 도메인 API로 통합
      - 전환 과정의 데이터 오류를 추적할 수 있도록 기존·신규 API 응답 비교와 마이그레이션 데이터 검증 절차를 분리
      - KRC와 JPW의 서로 다른 Kubernetes 클러스터를 gRPC로 연결하는 과정에서 HTTP/2 프록시 설정 문제가 반복됐고 팀 내 운영 경험과 참고할 레퍼런스도 부족했습니다. 문제 해결과 유지보수가 용이한 기존 HTTP Proxy 경로를 활용하도록 호출 방식을 REST로 전환하고 서비스 통신 설정과 배포 범위를 함께 정리
    result: |
      BL 조회 구조를 약 20개 테이블 조합에서 Cosmos DB 문서 1건 조회로 단순화했습니다. 운영 환경에서 동일 조회를 약 30회 측정한 결과 평균 응답 시간이 약 1,000ms에서 500ms로 줄었습니다.
      여러 애플리케이션에 흩어져 있던 조회 로직을 전담 도메인 API로 통합해 데이터 변경 시 수정 범위를 줄였습니다.
      REST 전환 이후 기존 gRPC 연결·프록시 오류와 동일한 유형의 문제는 발생하지 않았습니다.
    architecture:
      before:
        - 애플리케이션별 조회
        - 약 20개 테이블·API 조합
        - 중복 수정
      after:
        - 전담 도메인 API
        - Cosmos DB 문서 1건
        - 공통 조회 모델
